# NOMinate — Production Application Design

**Date:** 2026-06-15
**Status:** Approved (design); implementation plan to follow
**Author:** Ishita Kapoor (with Claude Code)

## 1. Purpose & Context

NOMinate is a meal-recommendation app: it learns a user's preferences and suggests
what to eat next, then helps them either cook it or order it out. The hackathon
prototype works as a click-through demo but is not a real product — it forgets every
user on restart, its ML model learns only from synthetic data, and it has no real
authentication or persistence.

This document defines the design for turning NOMinate into a production-grade
application with persistent storage, real authentication (including Google sign-in),
a genuine feedback-driven ML loop, and the infrastructure (config, tests, CI, Docker)
expected of a real project.

### Scope decisions (confirmed with user)

- **Database:** PostgreSQL via SQLAlchemy + Alembic migrations.
- **Auth:** Email/password (migrated to DB) **plus** Google OAuth (OIDC), issuing JWTs.
- **ML:** Full feedback loop — persist real ratings, give returning users real learned
  embeddings, and retrain on real + synthetic data.
- **Deployment:** Production-ready and fully deployable (Docker, env config, migrations,
  tests, CI), focused on running solidly locally first; live deploy is the final step.

## 2. Current State (baseline)

- **Frontend:** React + Vite + Tailwind, `react-router-dom`. Seven pages (LogIn, SignUp,
  ProfileSetUp, Response, Feedback, Cooking, TakeOut). All routes are public (no guards).
  API base URL hardcoded to `http://localhost:5001` in every component.
- **Backend:** Single-file Flask app (`What2Eat.py`) on port 5001. In-memory `users` and
  `profiles` dicts (lost on restart). Flask session cookies hold `profile`,
  `last_recommendation`, and `excluded_dishes`. Werkzeug pbkdf2 password hashing. Default
  secret key. CORS hard-pinned to `localhost:5173`.
- **ML:** PyTorch hybrid recommender — collaborative-filtering embeddings (user × dish)
  plus content-based side features (cuisine, skill, goal, budget, ingredient multi-hot)
  through an MLP. Trained on 500 synthetic users, ~596 dishes (TheMealDB), ~89k synthetic
  ratings generated by a deterministic `compute_rating` formula. New users are mapped to
  the embedding space by averaging the K nearest synthetic users' embeddings.
- **Restaurant lookup:** HTML scraping of Yelp (`yelp_scraper.py`) — fragile and against
  Yelp's ToS.
- **Feedback:** Appended to `ml/data/feedback_log.jsonl` but never read again.
- No tests, no CI, no migrations, no deployment config. `profile.json` is empty/leftover.

## 3. Problems This Design Solves

1. **No persistence** — users, profiles, recommendation history, and feedback all live in
   memory or session cookies and vanish on restart.
2. **ML can't actually learn** — the model only ever sees synthetic ratings; real feedback
   is logged but never used. Real users never get a real embedding.
3. **No real auth** — default secret, no token auth, no Google sign-in, no route guards.
4. **Fragile restaurant data** — Yelp scraping breaks easily and violates ToS.
5. **Unsafe constraint handling** — allergies are not enforced as a hard filter; dietary
   tags come from keyword heuristics.
6. **Not deployable** — no config separation, secrets management, tests, CI, or containers.

## 4. Target Architecture

```
nominate/
├── backend/
│   ├── app/
│   │   ├── __init__.py         # app factory, config wiring
│   │   ├── config.py           # env-based config (Dev/Prod), secrets from env
│   │   ├── extensions.py       # db, migrate, jwt, cors instances
│   │   ├── models/             # SQLAlchemy models (see §5)
│   │   ├── auth/               # email/password + Google OAuth, JWT issue/verify
│   │   ├── api/                # blueprints: profile, recommend, cooking, takeout, feedback
│   │   └── services/           # recommender wrapper, places client, retraining job
│   ├── migrations/             # Alembic
│   ├── tests/                  # pytest
│   ├── ml/                     # model.py, train.py, recommender.py (refactored)
│   └── seed.py                 # load dishes (+ optional synthetic users) into Postgres
├── frontend/                   # existing src/ moved here; AuthContext + ProtectedRoute
├── docker-compose.yml          # postgres + backend + frontend
├── .env.example
└── .github/workflows/ci.yml
```

The single-file `What2Eat.py` becomes a Flask app package created via an app factory.
ML code moves under `backend/ml/` and is consumed through a `services` wrapper so the web
layer never imports torch directly except via that boundary.

## 5. Data Model (PostgreSQL / SQLAlchemy)

- **users**
  - `id` (PK), `email` (unique, not null), `username`
  - `password_hash` (nullable — null for Google-only accounts)
  - `google_sub` (nullable, unique — Google subject id)
  - `created_at`
- **profiles** (1:1 with users)
  - `user_id` (FK, unique), `cuisines` (array), `dietary_restrictions` (array),
    `allergies` (array/text), `skill_level`, `weight_goal`, `budget`, `location`,
    `available_ingredients` (array), `updated_at`
  - Replaces both the in-memory `profiles` dict and the session `profile` blob. Editable.
- **dishes**
  - Mirrors the current CSV columns: `id`/`dish_id`, `dish_name`, `cuisine`, `category`,
    `dietary_tags`, `difficulty`, `calorie_tier`, `cost_tier`, `ingredients`.
  - Becomes the source of truth for the catalog (seeded from CSV); `dishes.pkl` retired in
    favor of DB reads (still cached in memory at engine load for scoring speed).
- **ratings**
  - `id` (PK), `user_id` (FK), `dish_id` (FK), `value` (numeric 1–5),
    `source` (enum: `explicit_feedback` | `cooked` | `takeout` | `liked` | `disliked`),
    `created_at`
  - The real training signal. Replaces the append-only `feedback_log.jsonl`.
- **recommendations**
  - `id` (PK), `user_id` (FK), `dish_id` (FK), `score`, `shown_at`,
    `action` (nullable: `cooked` | `takeout` | `rejected` | null)
  - Provides recommendation history and the persistent "recently shown / don't repeat"
    memory that currently lives in the session `excluded_dishes` list.

## 6. Authentication

- **Email/password:** migrate the existing flow to the `users` table; keep pbkdf2 hashing.
- **Google OAuth (OIDC):** use Authlib on the backend. Frontend obtains a Google ID token;
  backend verifies it, finds or creates a user by `google_sub` (falling back to email),
  then issues application JWTs.
- **Tokens:** JWT access token (short-lived) + refresh token. `Flask-JWT-Extended`.
  Protected API routes require a valid access token.
- **Frontend:** an `AuthContext` stores the session and a `<ProtectedRoute>` wrapper guards
  `/profilesetup`, `/generatedresponse`, `/feedback`, `/cooking`, `/takeout` (all currently
  public). A shared Axios instance reads the base URL from `VITE_API_URL` and attaches the
  auth header via an interceptor; the hardcoded `localhost:5001` URLs are removed.
- **Config:** `FLASK_SECRET_KEY`, JWT secret, Google client id/secret, and CORS origins all
  come from environment variables — no defaults committed.

## 7. ML — Real Feedback Loop

1. **Capture signal:** every feedback action, cook, and takeout writes a `ratings` row
   (e.g. "I just don't like it" → low value; cooking it → high value). Recommendations are
   logged to the `recommendations` table when shown.
2. **Real embeddings:** retraining includes real `user_id`s, so returning users receive
   genuine learned embeddings. The nearest-synthetic-user averaging is used **only** for
   brand-new users (true cold start).
3. **Retraining job:** `train.py` is refactored to read ratings from the DB (real signal)
   **blended with** the synthetic dataset, retrain the model, version the checkpoint, and
   hot-swap it into the running engine. Exposed as a CLI command runnable on a schedule.
4. **Inference fixes (in `recommender.py`):**
   - **Diversity / variety:** sample from the top-K scored dishes instead of taking a raw
     `argmax`, so "show me something else" yields genuinely different picks.
   - **Persistent exclusion:** read recently-shown dishes from the `recommendations` table
     instead of the session list.
   - **Allergy hard-filter (safety):** treat allergies as a strict exclusion layered on the
     existing dietary and skill filters. Any dish whose ingredients match an allergen is
     removed unconditionally.

## 8. Restaurant Data

Replace the Yelp scraper with the **Google Places API** behind a `services/places.py`
client, keyed by an environment variable. On missing key or API failure, fall back to the
current behavior (a helpful Yelp/Maps search link) so local development still works without
a key. The budget tiers map to Places price levels as the scraper currently maps them to
Yelp price filters.

## 9. Infrastructure & Quality

- **Docker:** `docker-compose.yml` runs Postgres, backend, and frontend together.
  `.env.example` documents every required variable. `config.py` separates dev and prod.
- **Migrations:** Alembic, with an initial migration creating all tables.
- **Seeding:** `seed.py` loads the dish catalog (and optionally synthetic users) into
  Postgres from the existing CSVs.
- **Tests:** pytest covering auth (email/password + Google verify path, JWT guards),
  profile CRUD, recommender filters (diet/skill/allergy hard-filters, exclusion), and
  feedback persistence.
- **CI:** GitHub Actions running lint + tests on push/PR.

## 10. Phasing (each phase independently shippable)

1. **Foundation** — restructure backend into an app-factory package; add Postgres, models,
   Alembic migrations; seed dishes; move frontend into `frontend/`.
2. **Persistence swap** — replace in-memory dicts and session state with DB-backed profile
   CRUD and persistent recommendation history.
3. **Auth** — JWT + Google OAuth + email/password on the DB; frontend `AuthContext` and
   route guards; env-driven API base URL.
4. **ML loop** — ratings capture, DB-driven blended retraining, inference fixes (diversity,
   allergy hard-filter, persistent exclusions, real embeddings for returning users).
5. **Restaurant API** — Google Places client replacing the scraper; secrets via env.
6. **Quality & deploy** — pytest suite, GitHub Actions CI, Docker Compose, deploy-ready.

## 11. Explicit Non-Goals (YAGNI)

- No switch away from the existing PyTorch model to SVD/other algorithms — the current
  hybrid model is adequate and blends real + synthetic data cleanly.
- No mobile app, no social features, no grocery-list/meal-plan generation in this scope.
- No real-time/online learning — retraining is batch/scheduled, not per-request.

## 12. Judgment Calls (reversible)

- **Keep the PyTorch model** rather than rewriting the algorithm.
- **Google Places** as the default restaurant source (broader coverage than Yelp Fusion);
  swappable behind the `services/places.py` interface.
- **JWT** (access + refresh) over server-side sessions, to keep the API stateless and
  deployment-friendly.
